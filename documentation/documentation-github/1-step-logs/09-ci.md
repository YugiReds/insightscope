# Step 9: Continuous integration (GitHub Actions)

**Result:** every push and pull request to `main` now runs the whole test suite on GitHub's machines, and the README shows a **Tests passing** badge. The first run passed in **1 minute 3 seconds**: 73 dashboard tests and 269 Python tests passed, with 1 skipped on purpose. No secrets are used. The Python suite grew to 270 tests.

**Date:** October 26, 2026 (morning)

## The goal

Prove on every change that nothing broke, without relying on "it worked on my PC". A green badge on the repo tells a recruiter the tests are real and run automatically.

## The big decision: what database does CI use?

Most Python tests read a database that's **filled with data** (counts, cross-checks, the `N/A` recall, spikes). GitHub's machine starts empty, and it must never get your local or Neon credentials. Claude Code inspected the tests first and laid out three options:

| Option | For | Against |
| --- | --- | --- |
| A. Fresh Postgres + download real openFDA data every run | Tests the real data and the ingest scripts | Slower. openFDA allows about 1,000 requests a day per IP, and GitHub's machines share IPs. The data changes weekly, so tests could go red with **no code change** |
| **B. Fresh Postgres + a small, fixed, made-up data set (chosen)** | No network, a few seconds, same result every run | About 150 lines to write and explain. Doesn't exercise real openFDA data |
| C. Skip the database tests in CI | Easy | Skips about two thirds of the suite, so the badge would mean little |

**Why B:** a CI badge is only useful if red always means "the code broke". With option A it could go red because openFDA was slow or its data shifted, and people learn to ignore a flaky badge.

## What was built

| File | What it does |
| --- | --- |
| `.github/workflows/tests.yml` | The workflow. Two jobs run **in parallel**: **Dashboard tests** (`npm ci --include=dev`, `npm test`) and **Python tests** (a Postgres 18 container, Python 3.12.10, `pip install`, build the dashboard, seed, `pytest`) |
| `tests/seed_ci_data.py` | Creates the tables and fills them with made-up data: 18 products, 412 recalls, 141 recall–NDC links. No random numbers and no "today", so every run is identical |
| `tests/test_ci_setup.py` | 31 tests for the guard, the seed data and the workflow file itself (versions match `render.yaml`, no secrets, actions pinned) |
| README badge + "Continuous integration" section | Shows the result of the latest run on `main` |
| `CLAUDE.md` "CI rules" | Seed only into `insightscope_ci`, keep CI secret-free, keep the seed deterministic |

## Decisions worth explaining in an interview

**A safety guard on the seed.** The seed deletes every row in the product and recall tables before inserting. It refuses to run unless the database name is exactly `insightscope_ci`, and it never reads `.env`. So it can't wipe your real database or Neon by accident. Claude Code proved the guard by switching it off on purpose: 10 tests failed.

**The made-up data is shaped for the tests.** It has repeated NDCs with different label dates, weekly reports on one weekday for over two years, two clear spikes 13 months apart (so one isn't inside the other's baseline), a recall numbered `N/A`, cells starting with `+` or `=` (for the CSV-injection guard), and a firm name with a comma. Every name is fake ("Example Pharma Inc").

**No secrets at all.** The CI database password (`ci-throwaway-password`) is in the workflow file on purpose: that database only lives for the few minutes of the job. There's no `HF_TOKEN`, and the AI tests use a fake client that fails any test trying to reach the network.

**Same versions as production.** Python 3.12.10, Node 24.15.0 and Postgres 18 match Render and Neon. A test fails if `render.yaml` and the workflow drift apart.

**Actions pinned to full commit SHAs.** For example `actions/checkout@3d3c42e…  # v7.0.1`. A tag like `v7` can be moved to point at different code. A commit SHA can't, so a hijacked action can't slip into your build.

**Least privilege.** `permissions: contents: read`: the workflow can read the repo but not change it.

**Cancel outdated runs.** A newer push to the same branch cancels the older unfinished run (`concurrency`), and each job stops after 10 minutes.

**Build the dashboard in the Python job.** That way the 4 tests that serve the real built dashboard run instead of skipping.

## Local proof before pushing

Claude Code created a separate local database, `insightscope_ci`, seeded it, and ran the full suite against it (DATABASE_URL set only for that one command): **270 passed, 0 failed, 0 skipped**. Against your normal database: also **270 passed**, with none of the old 239 results changed.

One test needed a small change: `test_the_real_database_is_not_touched_by_the_scratch_tests` checked `recalls > 1000`, which only fits the real data. It now checks `> 0`, which still answers "is the data still there?"

## Things to watch

- If a run goes red: **Actions** tab → the run → the red job → the red step. The last lines of the log say why.
- The badge only shows `main`. A red pull-request run doesn't change it.
- Real openFDA data isn't tested in CI. A separate, manual "live data" workflow could cover that later, kept out of the push check.

## How to see it

- Runs: https://github.com/YugiReds/insightscope/actions
- Re-run a run: open it → **Re-run all jobs**.
- Run the CI setup on your PC (optional): create the `insightscope_ci` database, then in one PowerShell window set `$env:DATABASE_URL` to it and run `.\venv\Scripts\python.exe tests\seed_ci_data.py`, then `.\venv\Scripts\python.exe -m pytest`. Close the window afterwards.
